# Mealprepped

A meal-prep planner. You tell it your diet, cuisines, servings and (optionally) what's already in your fridge. It suggests batch-cookable "clusters" of meals, lets you pick and schedule them across the week, then builds a grocery list.

## Stack

- **FastAPI** server, server-rendered with **Jinja2** templates
- **htmx** for partial page updates (card toggles, grocery checkboxes, substitutes)
- **Supabase** (Postgres) for per-user saved data
- **Google Gemini** (`gemini-3.6-flash`, via the `google-genai` SDK) for meal suggestions, recipe generation and ingredient substitutes
- **scikit-learn** TF-IDF for ranking recipes against the ingredients you already have
- **USDA FoodData Central** (optional) for nutrition lookups
- Google OAuth (Authlib) and signed cookie sessions

## How suggestions are generated

1. **Recipe data.** About 240 hand-curated recipes live in [recipe_data.py](recipe_data.py) as plain Python data (`RECIPE_DB`), with a meal type per recipe.
2. **Narrowing (only in "use what I have" mode).** If you list ingredients you already own, a TF-IDF index over the recipes (title, cuisine, meal type, keywords, ingredients, calorie tier) ranks them by cosine similarity to your ingredients, and the top 35 go forward. In "suggestions" mode there is no ranking step. The catalog is filtered by your selected cuisines, dietary needs and hidden recipes instead, and capped when no cuisine is selected.
3. **LLM step.** The candidate recipes are written into the Gemini prompt as a compact catalog (`[recipe_id] Title [cuisine] ... variations`). The prompt asks the model to choose clusters using exact `recipe_id`s and variation names from that catalog, and to return JSON.
4. **Expansion.** The server looks each returned `recipe_id` up in `RECIPE_DB` and fills in the title, image, ingredients and calories from the database.
5. **Plan page.** For each cluster, `/plan` uses the matching database recipe when there is one. Otherwise it asks Gemini to write the recipe, and falls back to a minimal card if that fails.

The catalog is enforced in code, not just in the prompt: any cluster whose `recipe_id` isn't in `RECIPE_DB` is dropped, and the hidden backup clusters the model also returns move up to fill the gap. If none of the returned IDs are valid, the user sees the generic error state. The model does still write recipe cards in one case: on `/plan`, a cluster with no name match in the database gets its recipe generated by Gemini (with a minimal fallback card if that fails).

## Run it locally

Requires Python 3.10+ (developed on 3.13).

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env     # then fill in the values
./start.sh               # or: uvicorn main:app --reload --port 8000
```

Open http://localhost:8000.

Environment variables (see [.env.example](.env.example)): `GEMINI_API_KEY`, `SUPABASE_URL`, `SUPABASE_KEY`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `USDA_API_KEY` (optional), `SECRET_KEY`.

Supabase needs a `user_data` table with columns `user_id` (primary key), `email`, `name`, `data` (jsonb) and `updated_at`.

## Project layout

- `main.py` is the FastAPI app, routes and the suggestion prompt
- `recipe_data.py` is the static recipe data (no logic)
- `recipe_index.py` is calorie estimation, the TF-IDF index and the prompt catalog builder
- `recipe_content.py` is cuisine/season constants and ingredient normalisation
- `recipe_gen.py` builds recipe cards: database match, then Gemini, then a fallback
- `grocery.py` builds the grocery list from planned recipes
- `nutrition.py` is USDA lookups and macro math
- `calendar_utils.py` is week/month helpers and amount scaling
- `llm.py` is the Gemini client and the single `_gemini()` helper
- `persistence.py` is Supabase load/save of per-user data
- `state.py` is the in-memory stores and session helpers
- `templates/` holds Jinja2 pages, with htmx fragments in `templates/partials/`
- `static/` holds CSS, JS, fonts and recipe images

## Known limitations

- **Login is not real authentication.** The email/name form identifies a user by a hash of their email, with no password. Google sign-in is available, but the email form is not safe for real user data.
- **Some server state is in memory.** For logged-in users, preferences and plans are saved to Supabase. The suggestion clusters, generated recipe cards and USDA macro results live in process dictionaries (`state.py`), so they are lost on restart and don't work across multiple workers. After a restart, accepted plans are still there and the recipe cards are regenerated.
- **Supabase errors are swallowed.** Load and save failures return empty data silently.
- **`main.py` is still the biggest file** (about 1,700 lines, mostly route handlers).
- **Some leftovers.** A few templates (`profile.html` and two partials) are unused.
- No automated tests.
- The default `SECRET_KEY` fallback is for development only. Set your own.
